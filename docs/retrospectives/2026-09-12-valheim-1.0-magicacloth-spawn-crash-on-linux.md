# Valheim 1.0: the spawn crash was cape physics, and the "unknown ZDOs" were never the killer

Date: 2026-09-12 (UTC; evening of 09-11 Pacific). Host: AM4 (`homebase`, Ubuntu, RTX 5070,
Valheim 1.0 build 25185596 = `l-1.0.7`, Unity 6000.0.75f1, via steamcmd at `~/valheim`). Repos
touched: `_retired/comfy` `handoffs/valheim-camera-proof` (commit `f8e3d46`, ComfyCameraProof
0.2.2). Follows [the 09-11 retro](2026-09-11-valheim-1.0-intro-cinematic-and-linux-prefs-path.md),
which left this crash as "the actual end of every 1.0 attempt".

Every 1.0 attempt on AM4 booted, skipped the intro (0.2.1), seeded prefs correctly (symlink
held, `ClothQuality 0` live), loaded the era11 world fully (`ZDOMan.Load is done [150,298ms]`,

## What the memory said, and what the logs say

The working belief coming in was "world saves were failing because the game was dying on
unknown ZDOs". That is a blend of two load-side events from 09-11, neither a save:

1. 06:29 UTC, root `era11-detail-v3-smoke-1.0b`: BetterServerPortals **1.7.0** threw
   `MissingFieldException` inside `PortalManager.ConnectPortals` ← `ZDOMan.Load`, and the game
   printed `World load failed, exiting without save. Check backups!` — its normal refusal to
   overwrite a world it could not load. Fixed the same day by building BSP 1.9.0 from
   `redseiko/ComfyMods a2b4680` against publicized 1.0 assemblies.
2. Every 1.0 load prints `Found 50087 ZDOs with unknown prefabs. Will load anyway.`, and a burst
   of `Missing prefab hash: -196905336` / `Destroyed invalid prefab ZDO:1:2458547…` lands seconds
   before the crash. That is the 1.0 client discarding the era's mod prefabs as the zone around the
   spawn activates. It happens on the passing run too (seven lines at 01:55:59, then more hashes
   at 01:56:18–20 with the player alive and shooting). Adjacent, not causal — the stack never
   touches ZDO code. The pre-1.0 client did the same thing at scale and never minded: OMEN's
   era12 run of 09-10 (`C:\work\valheim-capture\era12-omen-20260910\out\runs\batch-0000-attempt-01\Player.log`,
   0.221.12) logged 11,343 `Destroyed invalid predab ZDO` lines (the old build's own typo) and
   completed 564 shots; era10 logged 251 and stalled for an unrelated reason. What is new on 1.0
   is the explicit `Missing prefab hash` line (0 occurrences on 0.221.12) — and the cloth crash.

Nothing in any log, doc or receipt records a failed save. The harness never saves and never
disables saving; each attempt runs the world from a throwaway copy under `runs/<attempt>/xdg/`
(deleted on success), so whatever the 1.0 client writes back on quit never reaches `source/`,
whose hashes `check_runtime` verifies on every launch.

Two more memory claims did not survive reading: the crash was **not** fixed "in a separate Fable
session by another agent" (that session shipped the intro skip and the prefs symlink; its own
smoke died at spawn twice, and its retro lists the crash under *Still open*), and "reproduced on
`./valheim.x86_64` with no doorstop/BepInEx" is **unverified** — every vanilla 1.0 launch on disk,
on both hosts, was quit at the menu before a character was chosen. OMEN's one 1.0 Steam launch
(9/10 21:42 local) was also quit at the menu, so "Windows spawns fine on 1.0" is unverified too.

## What the 1.0 assemblies say (ilspycmd against the live 25185596 build, read-only)

- `VisEquipment.SetupCloth(GameObject)` is `private void`: for each `MagicaCloth` under the
  attached item it calls `Initialize()`, `DisableAutoBuild()`, merges `m_clothColliders` into the
  collider constraint list, then `BuildAndRun()`. It is the only caller that hands a cloth its
  colliders, and only colliders reach `AddColliderInternal`. Every `VisEquipment` (player and NPC
  humanoids) goes through it from `AttachArmor` and the shoulder path.
- Skipping `SetupCloth` alone would not be enough: `MagicaCloth.Start()` calls
  `ClothProcess.AutoBuild()`, which builds unless `DisableAutoBuild()` has set its state flag
  first. `SetupCloth` normally sets it; a prefix has to do the same before returning.
- `ClothQuality` (`ClothQualityManager.RefreshClothQuality`) only sets
  `MagicaManager.SetSimulationFrequency` (30/45/60/90) and the max simulation count per frame.
  It never disables cloth, so the `ClothQuality 0` experiments of 09-11 could not have worked.
- Other `MagicaCloth` users: `Ship.m_sailCloth` (prefab-authored, auto-builds in `Start`), the
  placement ghost, `PlayerClothWindShelter`. None hands over colliders; none crashed.
- Harmony was already proven on this exact Mono: BSP 1.9.0 detours `ZDOMan` there.
  `0Harmony.dll` (HarmonyX 2.9.0.0, 204,800 B) is in `BepInEx/core` on both hosts.

The player is hidden in every capture (`hideplayer`), so equipment cloth has no visual value to
the harness at all.

## What changed

`ComfyCameraProof` **0.2.2** (`_retired/comfy` `f8e3d46`; built on OMEN against its 25185596
assemblies; 93,184 B, sha256 `a3aa923a9c897df712625ec50f3498ff3688f094fcc017e6221651484581e3d4`):

- New config `Capture.skipEquipmentCloth` (default **true**, every platform — the project has
  already lost a day to a host-dependent difference). In `Awake`, wrapped in the same try/catch as
  the console-command registration, a Harmony prefix (`com.comfy.camera-proof.cloth`) on
  `VisEquipment.SetupCloth` calls `DisableAutoBuild()` on each `MagicaCloth` under the item and
  skips the original. The prefix binds the argument by position (`__0`), so a parameter rename in
  a later build cannot detach it. MagicaCloth2 types are reached by reflection only; the csproj
  gains `0Harmony` and nothing else, so builds without `MagicaClothV2` log "no cloth to skip" and
  carry on.
- New config `Capture.disableAllCloth` (default false): prefixes `MagicaCloth.BuildAndRun` and
  `ClothProcess.AutoBuild` too, so no cloth at all is ever built. A cfg edit on AM4, no rebuild,
  no re-stamp (the harness does not hash the cfg). Not needed.
- 0.2.1 (`24fa9c9e…`) parked at `~/valheim-capture/ComfyCameraProof.dll.0.2.1-24fa9c9e`, outside
  `plugins/` (any extra `*.dll` under `plugins/` is an `Unexpected plugin set`).
  `~/valheim-capture/launch-1.0-plugins.json` re-stamped with the new bytes/sha.

## What is settled

- The 1.0 blocker on AM4 was `MagicaCloth2` building cape physics at spawn on the Linux Mono
  player. Worked around at the mod; root cause (Mono/Unity 6000.0.75 vs. the BepInEx/doorstop
  environment) is not established, and does not need to be for the archive.
- The AM4 harness is back: 1.0, 25185596, plugin set 0.2.2 + BSP 1.9.0, `era11-detail-v5-smoke-1.0`
  green. The era11 detail tier can run as a full campaign from a fresh root.
- "Unknown ZDOs" are a load-time fact of playing an era world on a client without its mods, not a
  failure mode; they cost nothing and never touch `source/`.

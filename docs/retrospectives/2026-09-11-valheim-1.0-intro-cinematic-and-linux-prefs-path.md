# Valheim 1.0: the intro that has no saved state, and the prefs the harness never read

Date: 2026-09-11. Hosts: AM4 (`homebase`, Ubuntu, RTX 5070, Valheim 1.0 build 25185596 via
steamcmd at `~/valheim`) and OMEN (Windows, same build via Steam). Repos touched:
ComfyStewardView `tools/era-archive` (commit `1fd942f`), `_retired/comfy`
`handoffs/valheim-camera-proof` (commit `ad1d5f5`).

## What was being chased

After the 1.0 update the startup intro played on every launch of the AM4 capture harness. The
working theory for more than a day was that the harness launch path differs from Steam's Play
button in a way that stops the game saving or recalling an "intro already played" state. A
previous session seeded Unity prefs, re-seeded them at a second path, and diffed the profile
after a clean quit without finding a flag.

## Finding 1: the cinematic has no state. It plays on every cold launch, under every launcher.

Verified from the decompiled 1.0 assembly (`ilspycmd` on OMEN's live
`valheim_Data\Managed\assembly_valheim.dll`, 2,566,144 bytes, 2026-09-10):

- `FejdStartup.Start()` ends with `StartCoroutine(PlayIntroCinematic())`.
- The entire guard is
  `!Game.m_hasStartedOnce && CinematicsManager.s_instance != null && CinematicsManager.s_instance.m_introOnStartup`.
- `Game.m_hasStartedOnce` is `public static bool` with exactly one writer: the last line of
  `Game.Start()`, i.e. after a world has been entered in the same process. It exists to stop the
  video replaying when you quit to the menu. No PlayerPrefs or PlatformPrefs key (all 75 were
  listed), no file, no Steam Cloud entry, no Steam stat and no launch argument (all three
  argument parsers read) touches it.
- None of `CinematicsManager`, `PlayIntroCinematic` or `m_hasStartedOnce` exist in the
  0.221.12 or 0.213.4 decompiles. The cinematic is new in 1.0.
- Dismissal is `Escape`, `Jump` or `JoyButtonB` after frame 5 (`CinematicsManager.Update`).

The logs agree. Every 1.0 launch on record printed `Playing cinematic: $cinematics_intro`:
AM4 harness (08:12 UTC), AM4 manual with doorstop (06:45), AM4 vanilla (08:48), the two
experiment launches below (17:53), and OMEN's Steam Play-button launch (`Using environment
steamid`, 9/10 21:42:27 local). That OMEN session was its first on 1.0 and there has been no
second one, so "Play doesn't replay it" was never observed on 1.0. OMEN's registry
(`HKCU\Software\IronGate\Valheim`, 122 values), every AM4 prefs file and both hosts' Steam
cloud caches contain nothing intro-related.

Also true and previously unnoticed: the cinematic never blocked the auto-boot. The 08:12
harness run reached character select and world load underneath the video. Every 1.0 attempt
then ended at spawn with the MagicaCloth2 assertion (`result.json` `process-exit`); that is a
separate lane.

## Finding 2: on AM4 the game never read the prefs the harness seeded

Verified on AM4: the Unity 6 Linux player (`v6000.0.75f1`) read and wrote PlayerPrefs at
`unity3d/unknown/unknown/prefs`, never at `unity3d/IronGate/Valheim/prefs` where
`capture_worker.py` seeded them. Receipts:

- A 99-key seed at `IronGate/Valheim/prefs` was untouched after a run; the game's own
  write-back at `unknown/unknown/prefs` had 16 keys (Unity defaults plus session ids).
- Derek's maxed 1.0 graphics settings from the 06:45 manual session landed in
  `~/.config/unity3d/unknown/unknown/prefs` (101 keys, `profile = cap`), a file nothing seeded
  from. `~/.config/unity3d/IronGate/Valheim/prefs` still dated 09-09 02:36.
- This predates 1.0: the era14 run of 09-09 on build 21981559 wrote `unknown/unknown` too, and
  the directory was created on install day, 08-27 07:15.
- `Player.log` lists the save directory (`All files in local storage save data:`) and the Vulkan
  PSO cache lands in `/tmp/IronGate/Valheim`, so the product name resolves fine elsewhere.
  Only the prefs path is wrong, which is why the log looked healthy.

The experiment that settled the mechanism (`~/valheim-capture/prefs-experiment-20260911/`):
the same 1.0 binary, a fresh scratch `XDG_CONFIG_HOME` each time, no BepInEx, quit by
SIGTERM after the menu.

| Launch arguments | Prefs file written | When |
|---|---|---|
| `-console` | `unity3d/IronGate/Valheim/prefs` (17 keys) | at quit |
| `-console -screen-fullscreen 1 -screen-width 3840 -screen-height 2160` | `unity3d/unknown/unknown/prefs` (17 keys) | 1 s after launch, again at quit |

The player resolves its prefs directory at the first PlayerPrefs touch. With `-screen-*` on the
command line the screen manager touches it before PlayerSettings (company and product) are
loaded, so the names are empty and the path is `unknown/unknown` for the whole process. This
matches the only earlier launch that ever wrote to the correct path: the creator-dm run of
09-09 02:32, `valheim.x86_64 -console`, no `-screen-*`.

Windows is unaffected: OMEN's prefs are registry values under `IronGate\Valheim` and every
1.0 key is present there.

## What changed

1. `ComfyCameraProof` 0.2.1 (`_retired/comfy` `ad1d5f5`, built against OMEN's 25185596
   assemblies, 89,600 bytes, sha256 `24fa9c9e84791e25...`): `Awake` pre-sets
   `Game.m_hasStartedOnce` by reflection (config `Capture.skipIntroCinematic`, default true;
   no-op on builds without the field). After the local player appears, the auto-boot calls
   `Game.SkipIntro()` only while `InIntro(includeQueued)` is true, because a frozen character
   that has never spawned (`PlayerProfile.m_firstSpawn`, true for `cap.fch`) replays the
   in-world story intro and the valkyrie ride on every attempt. Not installed on OMEN's live
   plugin tree; `build-and-install.ps1` was deliberately not run.
2. `capture_worker.py` (ComfyStewardView `1fd942f`) seeds `xdg/unity3d/IronGate/Valheim/prefs`
   once and creates the relative symlink `xdg/unity3d/unknown/unknown -> ../IronGate/Valheim`,
   so read, write and seed are one file whichever name the player resolves. `result.json` now
   carries a `prefs` receipt: `keys`, `sha256`, `changedFromSeed`, `unknownIsSymlink`.
   `install_capture_worker.py` keeps `--prefs` and `gameBuild` from the previous session and no
   longer claims prefs can skip the intro.
3. AM4's real HOME was unified the same way: the newer `unknown/unknown/prefs` was copied over
   `IronGate/Valheim/prefs` (backup `prefs.bak-20260909-0236`), the old directory moved to
   `unknown.bak-20260911`, and `unknown/unknown` is now the symlink.
4. The plugin proof `~/valheim-capture/launch-1.0-plugins.json` was re-stamped with the new DLL
   hash; `install_capture_worker.py` refuses a root otherwise. A fresh root,
   `era11-detail-v4-smoke-1.0`, was frozen from the v3 root's `source/` with `questyfour` as the
   character and `prefs-capture-1.0.xml` (102 keys) as the seed.

## Verification run (`era11-detail-v4-smoke-1.0`, attempt 1, 17:59 UTC)

The first launch was refused with `disk-reserve`: AM4 had 20 GB free against the campaign's
21.5 GB floor. The bytes were 42 stale per-attempt scratch copies of the world database under
`*/runs/*/xdg/` (39 GB), which the worker itself calls disposable and only deletes on success.
Those files were removed (nothing under `source/` or `images/`), leaving 67 GB free.

Receipts from the attempt, all read from disk:

| Check | Result |
|---|---|
| Mod build loaded | `Loading [Comfy Camera Proof 0.2.1]` |
| Cinematic skipped | `Startup cinematic disabled: Game.m_hasStartedOnce pre-set before FejdStartup.Start.` and no `Playing cinematic` line in `Player.log` |
| Menu timing | `Valheim version` 17:59:29, `show character selection` 17:59:31, `OnCharacterStart "questyfour"` 17:59:33, `Load world` 17:59:36 |
| Story intro | no `Show intro` line (questyfour has spawned before) |
| Prefs path | `unknownIsSymlink: true`, `strayUnknownPrefs: false`, one `prefs` file in the tree |
| Prefs loaded and written through | `keys: 102`, `changedFromSeed: true` (sha `fa7822fa…` vs seed `489cf151…`); earlier attempts wrote back 16 keys |
| World | `ZNet.LoadOldWorld done [149,877ms]` 18:02:06, `Starting respawn` 18:02:10 |
| Outcome | `Caught fatal signal - signo:11` at 18:02:27, `result.json` `process-exit`, `portalCacheActive: true`, 0/1 shots |

The crash is the spawn-time end every 1.0 attempt has had, now reproduced with the operator's
real settings applied and no intro in the way. The last game lines before the signal are a
burst of `Missing prefab hash: -196905336` / `Destroyed invalid prefab ZDO:…`: the archive world
holds ZDOs of a prefab the 1.0 client cannot resolve, and the client was destroying them as
the player spawned. Adjacent, not proven causal. That is the next lane's first lead.

The worker's retry (attempt 2, 18:02:52 UTC) reproduced every receipt above and died the same
way at `Starting respawn` (18:05:32), this time with `signo:6` (SIGABRT, the assertion path the
previous session attributed to MagicaCloth2) rather than `signo:11`. The root ended
`failed / repeated-failure`, 0 of 130 shots. Two signals, one place: the crash is at character
spawn on the 1.0 client with this world, independent of the intro and of the settings applied.

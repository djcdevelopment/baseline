Level 1 — the concept

Everything is a prefab. Fields live on components.

Every object in Valheim — a wood wall, a goblin, a campfire — is a prefab. A prefab is a bag of components, and each component carries the fields that make the object behave the way it does. That's the whole trick behind custom fields:

A custom field belongs to a component, not to any one prefab. If you know a field on WearNTear, you can apply it to every prefab that has a WearNTear — walls, doors, carts, beehives.

Both prefabs carry Piece and WearNTear; only the campfire adds Fireplace. The fields live on the components — that's why one field reaches many prefabs.
Level 2 — the breakdown

Where the fields actually live

Components inherit from base classes, and the fields you're looking for are often declared up the chain. The classic trap: the goblin's health and run speed are not on Humanoid — they're on Character, its base class.

Level 3 — the code underneath

Lifecycle and the ownership contract

Only the owner of an object's ZDO may write its state. Everyone else asks. That single rule is why the RPCs exist, and it's the seam a Harmony mod hooks into.

Request-then-owner-writes is the whole multiplayer contract, visible in one component. Custom-field mods that write state directly on non-owners are the #1 source of "works solo, breaks in multiplayer."
